### 步骤 1：获取真实时间

📦 **产出物**：`date` 命令返回的时间戳

🔌 熔断器
├─ 成功条件：`date` 返回 YYYY-MM-DD HH:MM 格式的时间
├─ 失败处理：降级
├─ 可修正参数：—
├─ 重试次数：1
└─ 降级方案：时间字段留空，标注🟡降级，不阻塞执行

```bash
date "+%Y-%m-%d %H:%M"
```

**🔴 脚本承接时间戳（v3.10.5新增·第一性原理根治时间毛刺）**：
- ✅DO — 首选 `python3 [记忆共享中心]/技能配置/system-logger/scripts/append_log_entry.py --tool {工具}` 承接时间戳捕获：脚本内部 `date` 取 HH:MM + 解析当日日志路径 + 组头 tail 判定 + O_APPEND 追加 + 调 `reconcile_overview.py` 派生概览，最后打印真实块供 AI 回显。AI 只传**无时间值的条目体**（`完成：<NOW>` 占位），物理接触不到时间值 = 时间必为真（贴合本 Skill Poka-Yoke「物理接触不到错误源」）。
- ☑SHOULD — 自我思考类条目追加 `--reflection`：脚本在 `###` 标题前打 `[童灵思考]` 前缀（v3.10.15·v1.2 更名反思→思考·蒸馏管道按此标记分流 L2/L3/L6），AI 不手写该前缀——手写=标记可能与内容不符，分流即失真。
- ⛔DO NOT 手写字面时间戳。下方 `$(date)` 变量注入法仍允许，但若条目 `完成` 行出现字面 HH:MM 而非 `<NOW>` → `append_log_entry.py` 拒绝写入（exit 1）强制改用脚本。
- 根因：2026-08 日志第442行处曾写「20:46」而文件 mtime 14:35——AI 手填时间值 = 概率路径必漂；根治只能让 AI 碰不到时间值。

**铁律**：
- 通过 `date` 命令获取时间，命令执行失败时时间字段留空
- 这与 TE-20260425-001（未验证就下结论）属于同一类错误

**🔴 两步法阻断条件（v3.6.3新增·QD-013晋升·接触法·v3.6.5扩面）**：
- **适用范围（v3.6.5·用户拍板扩面）**：**任何含时间戳的文件写入**——系统日志、成长箱、台账、反哺日志、认知发现等一切带"完成/日期"字段的落盘动作，不限于系统日志——原因是QD-013第4犯（2026-07-28·promoted后漂移）恰栽在成长箱类写入：条文场景窄于错误场景=已晋升规则留了后门
- ✅DO 物理分两步：先**独立调用**跑 `date` 取锚点 → 得到返回值后，**下一次调用**才组装含时间戳的日志文本
- ⛔DO NOT 在同一次工具调用里既跑 `date` 又写含时间的日志文本（heredoc/脚本内嵌字符串）——原因是文本在调用生成时已写死，`date` 的返回值物理上不可能进入同调用的文本，该结构下时间必为编造（2026-07-27一日三犯实测：预写11:35/实际11:27、预写11:48/实际11:42、预写13:05/实际12:48，全部偏差）
- 阻断判定：发现"date与含时间文本同调用"结构 → 🔴 退回，先单独取锚点再重组文本；两步法实测零偏差（QD-013第三次写入验证）
- ✅DO 推荐实现（`$(date)`变量注入法）：`NOW=$(date "+%Y-%m-%d %H:%M")` 取值后在写入文本中引用 `${NOW}`——时间由 shell 展开，AI 不手写时间字符串（物理接触不到错误源）。与上条⛔禁令不冲突：禁的是"AI手写时间值"，注入法中AI写的是变量名非时间值。实测：2026-07-28 第5、6犯（v3.6.5扩面后仍漂移）改用注入法后，同日7次写入零偏差。**适用域（2026-09-01 Loop评估#2消歧）**：注入法适用于**系统日志以外**的含时间戳写入（成长箱/台账/反哺日志等——`append_log_entry.py` 不承接的场景）；系统日志域内本条已被 v3.10.5 脚本承接取代（脚本内部 `date`，AI 无时间值），`$(date)` 手动 `cat >>` 在系统日志域属绕过姿势（见步骤 3.2 ⛔）。
- `[来源: 成长箱反哺 | 日期: 2026-07-28 | 反哺标题: $(date)变量注入法（含时间写入物理防错）]`
- `[来源: 成长箱晋升 | 来源文件: qoder_errors.md QD-20260727-013 | 错误: 流程类·时间戳预写 | 晋升日期: 2026-07-27 | 扩面: 2026-07-28第4犯后用户认可·场景从系统日志扩至全部含时间戳写入]`

🔌 熔断器
├─ 成功条件：文件路径存在或可创建
├─ 失败处理：中止

### 步骤 2.5：写入前Read确认（v3.5.1新增）

📦 **产出物**：Read确认已获取文件现有内容

🔌 熔断器
├─ 成功条件：Read返回文件内容，或文件不存在的空结果正常通过
├─ 失败处理：中止
├─ 可修正参数：日志文件路径 → 检查日期是否正确，文件是否被锁定
├─ 重试次数：1
└─ 降级方案：无——Read失败不降级，不Write。Read可能因网络/IO延迟失败

**铁律（v3.5.1新增·防Write覆盖 / v3.6.1升级为设计端防误）**：
- ✅DO — 文件已存在时，执行Write前必须先用Read工具读取全文，确认文件中已有哪些内容。
- ✅DO — Write时，输出内容**必须包含全部现有内容+新增内容**，禁止只写新增部分而遗漏现有内容。
- ⛔DO NOT 假设"Write=追加"——Write是覆盖写入，传入什么就写什么，不会自动保留旧内容。
- 如果只是追加/修改日志中的部分内容，优先使用SearchReplace而非Write。
- **作用域限定（v3.10.3·M1审查候选）**：本节"Write包含全部内容+Section计数"防御仅适用于**新建骨架等整体Write场景**；条目追加一律走下方「整体读回写禁令」（cat >> 唯一合法姿势）。两条款并存不矛盾：前者防覆盖式Write丢内容，后者让条目场景根本不发生整体拼回——审查发现原铁律未限定作用域与禁令字面打架，本行消歧。
- 来源：TE-20260702-001（Write覆盖已有日志文件，现有内容丢失后从记忆琥珀备份恢复）

**🔴 Section计数校验（v3.6.1新增·设计端防误·接触法）**：
- ✅DO — Write前对比新旧内容的 section 数量：`grep '^## '` 旧内容 → N_sections，`grep '^## '` 新内容 → M_sections。
- 🔴 **M < N → 物理阻断，中止Write**。原因是新内容的 section 比旧内容少 = 部分内容即将被覆盖丢失——Read 成功但 AI 忘拼回去 ≠ 物理阻断，section 数字不符 = 物理阻断（接触法：数字是物理特征）
- ✅DO — 只在 M ≥ N 时允许执行 Write——确认所有原 section 均被保留（或至少数量级未下降）
- ⛔DO NOT跳过 section 计数直接 Write——原因是 Read+数 section=2 秒，覆盖丢失=无法恢复
- 来源：2026-07-18 T0 事故——AutoClaw 先 Read 了系统日志_2026-07-18.md 全文（工具返回完整），但 Write 时只写入了新增条目，原有 17 条 WorkBuddy 记录全部丢失。步骤 2.5 的 Read 环节本身成功——防护失败在"AI 记住并拼回去"这一步依赖认知而非物理锁

**🔴 结构健康门禁（v3.9.2新增·v3.9.4扩四条·v3.10.0封装单脚本·v3.10.17扩五条·防整体重贴/层级错位/正文塌陷·接触法）**：
- ✅DO — 写前必查：`python3 [记忆共享中心]/技能配置/system-logger/scripts/systemlog_gate_check.py 目标文件` 必须 exit 0（五查合一：h1唯一/概览唯一/体积<800KB/normalize工具名校验/SKILL.md正文完整性）。退出码语义：exit 1=通用错误（文件不存在等）、exit 2=一级标题异常（整体重贴）、exit 3=概览异常、exit 4=体积超限、exit 5=工具名/重复组违规、exit 6=SKILL.md 正文塌陷（本 Skill 的执行正文 <200 行）。任一非 0=文件已被异常整体重贴/膨胀/层级错位/组头重复，或本 Skill 已失去可执行正文 → 🔴 拒写 + 报警 + 先执行治理（备份至记忆琥珀→按一级标题整块去重→按条目工具字段重组→回验）再恢复写入
- 数字是物理特征：一级标题数≠1 = 整体重贴结构病，工具名违规 = 层级错位结构病（## 段承载条目内容），继续写只会加速恶化。写前确认改走 shell 通道（wc -c/grep -c/python3，**仅限只读核查命令**——非写入授权，条目写入仍唯一走步骤 3.2 脚本通道），不依赖受限读取工具
- 来源：2026-08-07 08-07 日志被整体自拼接 8 轮至 2^8=256 份副本（2.6MB/1794 条目行实为 10 条真实条目）；全机脚本无自追加逻辑、Skill 四副本路径一致，根因=Qoder CN 执行端"读全文写回"类操作实现为追加（用户认定·QCN-20260807-001）——门禁让此类异常写入物理上过不了门
- 来源（第五查）：2026-08-27 00:03 提交 `c564e9fe` 为改 frontmatter 一个字段，用覆盖式 Write 把本文件 639→11 行（`git show --stat` diff `632 +--------------------`），事故存活约 22h 且**过了全部既有守卫**——因为旧四查只扫日志文件、不扫 Skill 本体，写路径的"唯一合法通道声明"整段消失后 AI 便自寻 heredoc 旁路（同日 ②概览脏行、③追加旁路的共同上游）。第五查把"Skill 有没有正文"从认知依赖变成机械断言：阈值取最低合法正文量 200 行而非当前值——瘦身是常态，绑当前值=每次瘦身都要改数字

**🔁 组位不变式（v3.15.0·2026-09-10 跨组错位根治）**：
- `## <工具>` 段是条目的**归属容器**，不是时间序标记。但写入走 O_APPEND 时间序追加（铁律-014②：并发写不可约最优=追加，⛔禁「片段+合并+锁」）→ 多组文件里**非末位组**的新条目必然落在末位组名下（实证：WorkBuddy 条目落入 `## Trae Work`，概览计数同步错算 29/2 → 应为 30/1）
- 修法 = **写路径零改动**：① `append_log_entry.py` 机械保证每条携带 `- **工具**：<规范名>`（缺则补·与「完成」同机制·AI 零构造权）；② 组位归一由派生层 `reconcile_overview.py` 承担——按 `- **工具**` 字段把条目搬回所属组，**缺字段不动；无同名 `## 小节` 时补组头再搬（reconcile v1.3 建组再搬·脏值经 `_group_ok` 闸门⛔不猜）**，只搬行不改行
- 判据：**写者只追加，归一者管结构**——⛔DO NOT 在写路径上加锁或做读改写（那正是铁律-014②禁的 over-engineering：memlog 502→3022 行污染实证）
- 边界（刻意不做）：历史日志**不回溯重排**——历史是事实，批量改写冻结档案风险与收益不成比例；只保证向前正确

**⛔ 整体读回写禁令（v3.9.3新增·QCN-20260807-001晋升·防误层·v3.10.1作用域显式化）**：
- **作用域（v3.10.1）**：覆盖一切向系统日志文件的条目写入路径（日写入 + 月度蒸馏 D3 写当前日志）；蒸馏中心.md 的写入（D4）不属"写系统日志"但同样 ⛔DO NOT 整体读回写——✅DO 尾部追加或单锚点 SearchReplace。原因是作用域显式化前，本禁令原文与 monthly-distillation D3/D4 的"Write须包含全部现有内容"声明字面矛盾（2026-08-09 Loop评估发现），统一为追加姿势后矛盾消除
- ⛔DO NOT — 禁止「Read 全文 → 拼新条目 → 整体 Write 回写」模式写系统日志——2026-08-07 实测该模式一次失误=整体追加，此后每轮写入把已膨胀文件再次整体写回=按 2^n 指数放大（256 份/2.6MB 事故·Qoder CN 认领 QCN-20260807-001）
- ✅DO — 新增条目的唯一合法写入姿势：**经 `append_log_entry.py` 委托**——脚本内部执行 `cat >>` 追加仅新条目文本（O_APPEND 物理追加）→ 概览由 `reconcile_overview.py` 派生 → 写后 grep 回验（`grep -c '^### '` 应 +1）；修改已有条目用单锚点 SearchReplace（⛔DO NOT 全文拼回）。⛔DO NOT 把读到的旧内容拼进 new_text 整体写回。**"cat >>"指脚本内聚的物理姿势（2026-09-01 Loop评估#2消歧）——AI 手动 `cat >>` 绕过脚本属违禁（见步骤 3.2）**
- 原因：整体读回写是认知依赖型操作（靠 AI 记得拼回不重复），LLM 概率机制下必然失误；追加模式物理上不可能制造重复。与 v3.9.2 门禁（检测层）构成双防——门禁拦已发生的异常，禁令让异常无法发生

**⛔ 组头唯一性规则（v3.9.5新增·2026-08-08 重复组头复发实证·防误层）**：
- ⛔DO NOT — 追加条目时捆绑写组头（`## {工具}`）若该组已在文件中存在——重复组头=结构病（实测 2026-08-07 日志：WorkBuddy 组 2 次、Qoder CN 组曾 3 次）
- ✅DO — 追加前物理确认末尾组：`tail -5 目标文件 | grep '^## '`——末尾组=本工具 → 直接追加条目（不带组头）；末尾组≠本工具 → 追加 `## {工具}`+条目（组头合法出现一次）；**grep 为空（窗口落条目内——8字段条目≥10行 > 5行窗口·常态场景）→ 扩窗 `tail -30` 再找组头判定；仍空 → 按"末尾组≠本工具"处理追加组头（保守分支·v3.10.3 M3补定义）**
- 写后回验：`grep -c '^## {本工具名}' 目标文件` 不得比写前增长（首次建组除外）
- 与 v3.9.4 门禁第四条（normalize_tool.py v0.2 起含重复组检测）构成双防——规则让重复组写不出，检测让已发生的重复组过不了门

### 🔧 自修复通道（v3.10.9 新增·根治写入端绕过归一化·2026-09-01 Loop评估#7归属对齐CHANGELOG）

**✅DO — 部署写时守护（根治·非检测）**：**macOS** 跑 `bash [记忆共享中心]/技能配置/system-logger/scripts/systemlog_watch.sh`、**Windows** 跑 `powershell -ExecutionPolicy Bypass -File <MC>\技能配置\system-logger\scripts\systemlog-watch.ps1`（轮询快照版），监听日志目录，任何 `系统日志_*.md` 变更后防抖 2s 跑 `systemlog_normalize_fix.py`：把非规范 `## ` 头按条目 `- **工具**：` 字段归组、降为 `### ` 清洗标题；按条目字段把 entry 重排到正确 `## {工具}` 组。覆盖所有写入端（含 AutoClaw 直写），异常在下次写入即自我消解。

**⛔DO NOT 在工具字段加 emoji / ⚡ / 括号注释 / 变体拼写。**
**⛔DO NOT 用 identity 原始值直落盘——落地前 ✅DO 先归一。**

**🔒 格式契约适用范围（v3.10.9 第一性原理根治·文件范围化）**：本 Skill 的格式契约是**文件级契约**——适用于**所有写入 `系统日志_YYYY-MM-DD.md` 共享文件的端**，⛔DO NOT 与 `compatibility` 字段绑定。根因：日志的一致性（跨端可读/可聚合）是「文件」的属性，不是「写入者身份」的属性；把格式合规边界误设为「端范围」并依赖手动端清单做 Enforcement → 清单遗漏即漏洞（AutoClaw 掉出列表即实证）。`compatibility` 字段仅声明「本 Skill 工作流在哪些宿主可执行」的**平台元数据**，⛔DO NOT 当作格式合规闸门。未列端（如新增 DeepSeek Harness 忘了登记）写出违例 → **写时守护（v3.10.8）端无关自动修复**，遗忘新端 ≠ 复现 bug。格式守两条：①读 spec 的端从源头不写错（本规范）②所有端写错由守护兜底（结构锚点化+归组）。
