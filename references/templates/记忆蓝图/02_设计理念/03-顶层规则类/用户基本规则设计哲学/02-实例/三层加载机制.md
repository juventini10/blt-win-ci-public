## 实例一 · 三层加载机制（渐进式披露实操）

> 本章从原则层（01 §三/§四）落到操作层——读完即可理解"AI 在运行时怎么触达用户基本规则"，不需要返回讨论"为什么"。

### 1. 三层触发流（运行时真实路径·通用模型）

```
每会话启动
  └─ BootstrapLoader 自动注入 MEMORY.md 前 N 行
       ├─ 铁律骨架段：核心铁律已内置 + 三文件指针 + 版本校验行
       └─ 常驻触发句："涉及规则执行→扫描铁律版头部加载时机索引表→匹配则 Read 细则"
  ↓ 对话进行中
  ├─ 高频场景 → 行为画像常驻（见 01 通用规范·压缩态常驻替代脚本硬墙）
  ├─ 规则场景（删除/写入/引用/创作…）→ 铁律版加载时机索引表匹配 → Read 对应细则
  └─ 边缘场景（冲突/修改/深度解释）→ 详解版按需 Read（执规/冲突检测）
```

**关键事实**：三层文件（摘要版/铁律版/详解存档）均**不进任何端 rules 自动注入目录**——常驻的只有 MEMORY.md 调度层（压缩不可删的核心条款）。这是"渐进式加载"在运行时的真落地。

### 2. 加载时机索引表（铁律版自描述触发）

**机制**：每条铁律在铁律版头部携带一句完整自然语言触发条件（加载时机列），AI 扫描→匹配→Read 细则。触发逻辑完全内聚于规则文件，MEMORY.md 只存一条指向指令。

**编写原则**（why 而非 what）：
- 每条加载时机是一句**完整自然语言条件**，AI 做 `if 用户输入 contains 加载时机关键词 → Read 对应细则`
- 已内置项标注"已内置"而非省略——保留完整行让索引表不丢条目，但明确不需额外 Read
- 加载时机描述**场景**而非**操作**——"收到请求时"而非"执行 Read 后"（条件不自引用）

**示例（铁律版索引表节选）**：

| 编号 | 名称 | 加载时机（触发条件句） | 口诀 |
|:----:|------|------------------------|------|
| {{001}} | {{先看清，再动手}} | 涉及文件修改/创建/删除/移动/覆盖/批量操作的任务指令，执行前先确认现状 | {{分析→呈现→确认→执行}} |
| {{002}} | {{实事求是底线}} | 输出涉及数据断言、数字、事实引用、文件路径、代码模式、"记忆中说"的内容、写入记忆时 | {{未验证标⚠️，没读过不编}} |

> 完整索引表以你的铁律版头部为 SSOT，本文件夹不重复承载规则内容。

### 3. 启动级版本校验（最高可靠形态）

```
每次对话启动 → Read 铁律版头部版本号（前 N 行）
  ├─ 版本号 ≠ 记忆中版本号 → Read 铁律版全文 + 更新记忆版本
  └─ 版本号 = 记忆中版本号 → 信任当前规则，仅按需触发铁律
```

- **落点**：MEMORY.md 铁律骨架段（BootstrapLoader 自动注入）
- **成本**：Read 铁律版头部数行，可忽略
- **本质**：不是"规则全文注入"，而是"每次对话先确认规则没变"——自动读取+比对即在此实现
- 详见 `WB平台物理约束.md`（物理约束下为何只能如此）

### 4. 加载时机 vs 关键词匹配（历史演进·方法论）

**旧方案缺陷**（MEMORY.md 硬路牌关键词列表）：
1. **自举悖论**：AI 需匹配"场景"→但不知铁律有哪些，"匹配"无从谈起
2. **维护分裂**：触发锚点在 MEMORY.md，细则在铁律版，加新铁律要改两个文件
3. **信息损失**：口诀不足以精确判断"当前是否触发"

**优化后**（铁律版自描述加载时机）：触发逻辑完全在铁律版内部，MEMORY 只存一条指向指令。加新铁律→只在铁律版加一行索引，不碰 MEMORY。

### 5. 单文件 vs 三文件（对标结论·模板）

| 维度 | 单文件宪法 | 三文件分层 |
|------|----------|-----------|
| 维护成本 | 低（一处改） | 中（改规则需同步三处版本号） |
| 读取效率 | 低（读头部够但同文件） | 高（摘要版触发路由层·铁律版按需 Read） |
| 扩展性 | 弱（行数多后拥挤） | 强（详解版历史不挤占轻量入口） |
| 规则发现 | 强（加载时机在规则旁） | 强（铁律版头部索引表自描述） |
| 注意力预算 | 优（头部→匹配→读详细） | 优（摘要版触发路由→匹配→读铁律版） |

**结论**：三文件在规模上更优，触达效率通过对齐单文件自描述加载时机已补齐。
