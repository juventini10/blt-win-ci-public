## 实例二 · 平台物理约束下的规则加载模型

> **来源**：讨论"用户基本规则能否自动让系统读取"→查阅平台权威资料→发现平台物理天花板
> **理论依据**：所用 AI 编码助手的官方指南（MEMORY.md 前 N 行注入说明）+ 平台源码分析（BootstrapLoader 行为）+ 社区实测报告（上下文压缩机制）

### 1. 三层物理约束

用户基本规则要"系统级自动加载"，不可绕过以下三层物理天花板：

```
Layer 1: BootstrapLoader 系统注入
├── 每次对话启动时自动执行
├── 加载文件：SOUL.md + IDENTITY.md + USER.md + MEMORY.md(前 N 行)
├── 预算上限：约 20,000 字符（多文件共池）
└── 不可跳过——平台层保证

Layer 2: MEMORY.md 硬路牌触发（可由 UserPromptSubmit 预注入机械强化）
├── 随 Layer1 注入（前 N 行以内）
├── 条件触发：「规则场景时」→ Read 铁律版索引表 → 匹配铁律
└── 可被上下文压缩影响（但预注入在 UserPromptSubmit 早于压缩，不受影响）

Layer 3: Context Compression 天花板
├── 一定阈值触发轻量压缩（重述对话、精简工具输出）
├── 更高阈值触发深度压缩（旧信息压为摘要）
├── 无豁免——系统注入和对话内容一视同仁
└── 压缩后规则可能只剩摘要中的半句话
```

**核心推论**：用户基本规则要"系统级自动加载"，只能抢占 MEMORY.md 前 N 行内的黄金位置。Layer2 和 Layer3 的不可靠性意味着——规则要么在 Layer1 注入时自带进来，要么就可能在所有对话中不可达。

### 2. 版本校验：「自动系统读取」的最高形态

在平台物理约束下，"规则全文自动注入每次对话上下文"是不可行的（注入池已满 + 压缩无豁免）。最高可靠形态是**启动级版本校验**：

```
每次对话启动 → Read 铁律版头部版本号（前 N 行）
  ├─ 版本号 ≠ 记忆中版本号 → Read 铁律版全文 + 更新记忆版本
  └─ 版本号 = 记忆中版本号 → 信任当前规则，仅按需触发铁律
```

- **落点**：MEMORY.md 铁律骨架段（前 N 行，BootstrapLoader 自动注入）
- **成本**：Read 铁律版头部数行(~1KB)，可忽略
- **本质**：不是"规则全文注入"，而是"每次对话先确认规则没变"——自动读取+比对即在此实现

### 3. 规则设计的反推原则

从三层物理约束反推规则文件的设计原则：

| 约束 | 反推原则 |
|------|---------|
| 前 N 行 = 金矿 | 核心约束（版本校验、硬路牌、关键路径）必须优先占用此位置 |
| 字符共池 | 不在 MEMORY.md 放非紧急内容——占用的是其他系统文件的预算 |
| 压缩无豁免 | 规则触发逻辑必须具备 fallback——"若上下文压缩导致索引表不可达，默认按核心铁律覆盖" |
| Layer1 不可跳过 | 版本校验借 Layer1 注入 → 自动执行，不依赖 agent 记性 |

### 4. ADR-008：规则加载机制从"被动条件触发"升级为"启动级版本校验+条件触发兜底"（模板）

- **日期**：{{填写决策日期}}
- **决策**：在 MEMORY.md 铁律骨架段追加版本校验行，每次对话启动时自动 Read 铁律版头部版本号比对。
- **理由**：查阅平台权威资料后确认——MEMORY.md 前 N 行由 BootstrapLoader 自动注入（不可跳过），但 Context Compression 对系统文件无豁免。规则全文注入不可行，版本校验是物理约束下的最高可靠形态。
- **实施**：MEMORY.md 铁律骨架段追加版本校验行（在 N 行以内）；版本号位置——铁律版 frontmatter `version:` 字段（前 N 行）。
