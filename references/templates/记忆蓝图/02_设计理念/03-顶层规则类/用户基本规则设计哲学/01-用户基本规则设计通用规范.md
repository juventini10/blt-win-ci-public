## 用户基本规则设计通用规范（模板）

> **宪法（最高行动纲领）**：本规范一切原则/反模式服务 `00-宪法愿景.md`——用户基本规则是行为约束层，靠三层分离+渐进式披露在你的平台物理约束下可靠触达 AI。**若本规范任何条目与宪法冲突，以宪法为最高判据。**

本规范抽象「行为约束如何被分层、加载、防漂移」的共通原则，是判定用户基本规则设计的标尺。它不描述任一机制的执行细节（那在 `02-实例/` 分域记录），只回答"规则体系的根靠什么成立、怎么验证、怎么进化"。

## 一、用户基本规则的第一性目的

**让 AI 在每一次会话都先知道"不可逾越的底线在哪"，且只在需要时才付出读取成本——三层分离（摘要/铁律/详解）按注意力预算渐进披露，在平台物理约束下靠启动级版本校验+用户输入预注入+会话结束钩子机械兜底，实现"可靠触达而不浪费上下文"；并靠三层防护体系（脚本抗体/代理检测/恒驻注入）实现"读到后确实执行"，从文本约束升级为硬约束。**

用户基本规则做三件事（三层生命周期）：
- **常驻调度**：每会话自动上场，告诉 AI"去哪找、版本对不对"，并内联行为画像压缩段
- **按需深查**：铁律版加载时机索引表 → 匹配细则；详解版边缘情况深查：触发时才付出读取成本
- **机械兜底**：多挂点（用户输入钩子预注入铁律段 + 会话结束钩子校验三层一致 + 免疫扫描抗体）：升版漏改一层即告警·铁律复发即被脚本逮出

## 二、第一性原理：为什么三层分离而非单文件

**三层的本质 = 信息稳定度 × 读取频率梯度**（与记忆系统"稳定度梯度"同构）：

```
铁律版（命令层）  ← 最稳定+最高频触发：N条"做什么/不做什么"，每次对话可能命中
摘要版（上下文层）← 中稳定+中频：用户是谁+协作契约，进会话即需但不必全读
详解版（裁决层）  ← 低频：冲突/修改/边缘解释/执规，仅少数场景深查
```

**层划分的判定标准（二分判据）**：一条规则入哪层，问两个问题——①它多久变一次？（稳定度）②它多常被触发？（读取频率）。越稳定+越高频 → 越靠铁律版；越易变+越低频 → 越靠详解版。

**为什么不是单文件**：详解版体量过大无法塞入单文件——单文件宪法把"头部轻量+底部详情"内化，但你的详解版远超单文件承载力，三文件物理隔离是唯一可维护解（详见 `02-实例/三层加载机制.md`）。

## 三、设计溯源：四路权威理论（保留·可迁移）

### 3.1 Constitutional AI (Bai et al., 2022)
**核心主张**：用少量自然语言原则替代大规模人类反馈标签，通过"批判-修订"循环将原则转化为监督信号。
- 宪法是少数可读原则 ↔ 你的 N 条铁律
- 批判-修订循环 ↔ 成长箱蒸馏（人批判 AI → 晋升铁律）
- 原则多样性 > 单一原则 ↔ 核心 1 条强启动 + 其余按触发预注入（注意力预算最优）
- 透明可读 ↔ 三层分离（摘要一眼扫完/铁律完整可读/详解可审计）

### 3.2 Instruction Hierarchy (Wallace et al., 2024)
**核心主张**：LLM 应建立指令优先级——System > User > Tool Output。
- System > User > Tool ↔ 系统注入 > 用户规则 > 外部数据
- Context Ignorance 训练 ↔ 实事求是（不确定不瞎编）
- 对齐/不对齐指令区分 ↔ 意图分类（每轮先分类再回答）

### 3.3 Context Engineering (Anthropic, 2025)
**核心主张**：上下文是有限资源（注意力预算），应通过"渐进式披露"让 Agent 逐层发现信息。
- 注意力预算（n²关系稀释）↔ 常驻 ≤ 上限字符
- 渐进式披露 ↔ 三层文件结构（摘要→铁律→详解）
- 最小高信号令牌集 ↔ 常驻只放"触发开关+口诀"
- 按需加载是扩展模式 ↔ Skill 按名加载

### 3.4 Agent Constitution (GitHub, 2026)
**核心主张**：将 Agent 行为规则声明为 YAML 配置（rule_name/condition/action/severity），运行时评估。
- YAML condition ↔ 铁律版"加载时机"列（规则自带触发条件）
- block/notify 动作分类 ↔ 五级标注（DO NOT/DO/SHOULD NOT）

### 3.5 标杆对标（示例）
| 维度 | 单文件宪法 | 三文件结构（你的方案） |
|------|:----------:|:------------:|
| 入口文件 | 单文件 co_mechanism | MEMORY.md（路径索引+版本校验） |
| 规则组织 | 同文件分级 | 摘要/铁律/详解（三文件物理隔离） |
| 触发机制 | ✅ 加载时机 | ✅ 铁律版加载时机索引表 |
| 强制程度 | 🔴 不可跳过 | 🔴 铁律版头部宪法级声明 + 五级标注 |
| 机械兜底 | ❌ | ✅ 输入预注入 + 结束钩子校验 + 抗体扫描 |
| 落地层覆盖率 | ❌（纯文本约束） | ⚠️ 分类完成 ≠ 落地完成 |

**结论**：三文件结构在规模上更优，触发效率通过对齐单文件的自描述加载时机已补齐；预注入硬墙进一步将"按需 Read"升级为"预防"。属愿景对齐的质变。

## 四、核心设计原则

### 原则一：注意力预算优先
规则的注入必须服从上下文窗口的稀缺性。只注入"触发开关"（路径+触发条件），不注入"执行手册"（完整细则）。

### 原则二：触发条件自描述
每条规则自身携带"我何时生效"的触发条件。AI 扫描所有规则的触发条件，匹配→加载。

### 原则三：渐进式三层披露
第一层（摘要版）：高频场景速查 → 第二层（铁律版）：N条铁律完整约束 → 第三层（详解存档）：边缘情况和深度解释。

### 原则四：单点触发、单向依赖
MEMORY.md 是唯一的规则入口。铁律版不反向引用 MEMORY.md。摘要版不反向引用铁律版。依赖箭头永远单向：MEMORY → 铁律 → 详解。

### 原则五：硬约束优于软建议
规则的强制性声明必须在规则自身，而非外部注释。"不可跳过"是规则的一部分。

### 4.1 三层分离的设计理由
| 为什么不是单文件？ | 理由 |
|------------------|------|
| 详解存档体量过大 | 塞进一个文件 → 每轮注入爆炸 |
| 摘要版高频 Q&A | 需独立快速扫描——混在铁律版干扰细节 |
| 铁律版完整铁律 | 需独立完整性——混在摘要版丢失细节 |
| 版本同步 | 三层共享版本号——改一处升三处，是同步成本也是完整性保证 |

**三层分离不是过度设计，是语义隔离**：摘要版回答"用户是谁"，铁律版规定"AI 怎么做"，详解存档解释"为什么"。

### 4.2 强制程度分级（五级标注体系）
| 级别 | 声明方式 | 适用范围 |
|:----:|---------|---------|
| 🔴 宪法级 | "不是建议，是硬约束。不可跳过" | 铁律全文 |
| 🔴 系统级 | ⛔DO NOT / ✅DO / ☑SHOULD NOT | 单条铁律具体禁止/强制 |
| 🟡 路由级 | "触发时→Read" | 铁律索引表加载时机 |

| 标注 | 含义 | 例外 |
|:----:|:-----|:-----|
| ✅ **DO** | 必须采纳 | 需例外须事先说明理由 |
| ☑ **SHOULD** | 强烈建议 | 有合理理由时可例外 |
| **MAY** | 可选 | 自由判断 |
| ☑ **SHOULD NOT** | 强烈不建议 | 有合理理由时可例外 |
| ⛔ **DO NOT** | 禁止采纳 | 需例外须事先说明理由 |

## 五、三层三角最终定位 + 工程原则

### 5.1 三层三角
```
铁律版 (命令层)   — "做什么、不做什么" — N条+加载时机 — 双模式（内置注入+按需Read）
摘要版 (上下文层) — "在跟谁说话" — Q&A+速查 — 文档结构索引+按需参考
详解版 (裁决层)   — "看不清时怎么办" — 执规+冲突+琥珀 — 按需Read
```
三者职责无重叠、依赖单向（MEMORY→铁律→详解）、规模最优化。

### 5.2 三层分离的工程原则（三项独立来源交叉验证）
| 原则 | 来源 | 约束 |
|------|------|------|
| 最小充分披露 | Context Engineering："系统提示只放稳定高信号指令" | 详解版只保留其他两层无法替代的内容 |
| 单一职责 | Zylos Research："每段注入只有一个清晰目的" | 铁律=命令层、摘要=上下文层、详解=裁决层 |
| 连贯性最大化 | Anthropic：上下文污染使多步任务准确率暴跌 | 详解版只保留"AI 碰到铁律不够用时才会翻"的内容 |

## 六、规则 TTL（时效管理）

**设计来源**：知识半衰期问题——部署后准确率随时间下滑；不同内容以不同速率衰减。规则亦然。

### 6.1 三层 TTL 模型
三层规则文件高度联动——改一层必然波及另外两层。因此 TTL **三层统一采用 90d（季度审视）**，同时审视、同时更新、同时升级版本号。

| 层级 | 对应文件 | TTL | 过期处理 |
|:----:|---------|:---:|---------|
| 铁律版 | 底线原则（变动极少） | **90d** | 统一审视，有冲突时更新版本号 |
| 摘要版 | 用户速查（习惯漂移） | **90d** | 统一审视，习惯漂移时更新 |
| 详解版 | 边缘细则（随使用变化） | **90d** | 统一审视，过期规则归档至记忆琥珀 |

**归档策略**：失效但不丢弃——旧事实不覆盖，只关闭（invalidate-but-don't-discard），归档保留原内容+失效日期+失效原因。
